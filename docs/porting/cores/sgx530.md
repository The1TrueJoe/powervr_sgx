# SGX530 (TI OMAP3630)

The fact sheet for the second core: the PowerVR SGX530 in TI's OMAP3630 / DM3730 family
(ARMv7 Cortex-A8). It collects what public sources say, compares it with the SGX545 we
know from hardware, and lists what a hardware test must confirm before any of it goes into
the driver tables. Facts read on an OMAP3630 board since 2026-11-13 carry the **C** tag.

The method is [state.md](../state.md)'s: every fact carries a tag. A fact stays below
**C** until our own hardware read confirms it, however good its source.

| Tag | Meaning |
|---|---|
| **L** | Mainline Linux 7.3.3: the device tree, its binding, or a driver. The text is in the tree. |
| **K** | The GPL kernel side of an SGX DDK: its register, feature, errata and MMU headers. They describe what that DDK programs, not the silicon itself. |
| **D** | Derived from L or K facts, often with an SGX545 result we confirmed on hardware. |
| **C** | Confirmed on SGX530 hardware (an OMAP3630 board), with its date. |
| **G** | A guess. |
| **U** | Unknown. |

## Sources

- **L:** `Documentation/devicetree/bindings/gpu/img,powervr-sgx.yaml`,
  `arch/arm/boot/dts/ti/omap/omap36xx.dtsi`, `omap3.dtsi`,
  `omap36xx-am35xx-omap3430es2plus-clocks.dtsi`, `drivers/bus/ti-sysc.c`,
  `arch/arm/mach-omap2/powerdomains3xxx_data.c` and `clockdomains3xxx_data.c`.
- **K, SGX530:** the GPL-2 kernel headers of an SGX530 rev 125 DDK (1.4 series):
  `sgx530defs.h`, `sgxfeaturedefs.h`, `sgxerrata.h`, `sgxmmu.h`.
- **K, both cores:** the GPL kernel drop the SGX545 work started from: its `sgx545defs.h`,
  `sgxfeaturedefs.h`, `sgxerrata.h`, `sgxmmu.h`, and the host-side workaround code in
  `sgxutils.c`.
- **L, SGX530:** TI's full autogenerated `sgx530defs.h` (rev 1.15), which also names the TA,
  DPM, ISP, PDS and VDM registers. Cleared by Joseph on 2026-11-27 for reference: facts
  only, nothing copied.
- **L, SGX535:** img-sgx, a public GPL-2.0 SGX535 driver whose kick and heap-load sequences
  are transcribed from a closed driver. Cleared for reference the same day; its sequences
  stay leads until hardware confirms them.
- No closed userspace or firmware was used.

The DDK's register headers list only the registers the host kernel touches. The TA, 3D,
DPM, ISP, TSP, PBE and PDS state registers that the microkernel and the command streams
program aren't in them, for either core. Everything about those is **U** for the SGX530.

The expected revision is derived two ways:
- The DDK writes revisions as decimal digits, major.minor.maintenance. The SGX545's "1014"
  is the 1.0.14 our CE5300 reads as `0x0001000e`, and "1013" is Cedarview's `0x0001000d`
  (hardware). So 125 is 1.2.5.
- `ti-sysc.c` matches an OMAP34xx GPU by reading offset 0x14 of the module and expecting
  `0x00010201`: rev 121 in that encoding, at the 0x14 `sgx530defs.h` gives for
  `CORE_REVISION` (L).

## Register map differences from the SGX545

Offsets are from the start of the GPU's register window. The SGX545 column is from its K
header; where we confirmed an SGX545 register on hardware, the hardware agrees with it.

### Moved

|---|---|---|---|
| `CLKGATESTATUS` | 0x0004 | 0x0008 | K |
| `CLKGATECTLOVR` | 0x0008 | 0x000c | K |
| `CORE_ID` | 0x0010 | 0x001c | K |
| `CORE_REVISION` | 0x0014 | 0x0020 | K |
| `DESIGNER_REV_FIELD1` | 0x0018 | 0x0024 | K |
| `DESIGNER_REV_FIELD2` | 0x001c | 0x002c | K |
| `PDS_INV3` | 0x0adc | 0x0ad8 | K |

On the SGX545, 0x0004 is `CLKGATECTL2`. A driver that reads 0x0008 as the clock status on

| Register | Offset | Tag |
|---|---|---|
| `PDS` | 0x0abc | K |

The SGX545's `EVENT_KICK1` to `3` (0x0ae4 to 0x0aec) have no SGX530 register. Don't reuse

### Only on the SGX545 (absent from the SGX530 header)

## Clock gating

| | SGX530 | SGX545 | Tag |
|---|---|---|---|
| Gated units | 2D, ISP, TSP, TA, DPM, USE: one 2-bit control each | ISP, ISP2, TSP, TE, MTE, DPM, VDM, PDS0 and more | K |
| `CLKGATECTL` | 2D b0-1, ISP b4-5, TSP b8-9, TA b12-13, DPM b16-17, USE b20-21, auto/manual b24 | ISP b0-1, ISP2 b2-3, TSP b4-5, TE b6-7, MTE b8-9, DPM b10-11, VDM b12-13, PDS0 b14-15; auto/manual b24 | K |
| `CLKGATESTATUS` | 2D b0, ISP b4, TSP b8, TA b12, DPM b16, USE b20 | 20 units, one bit each (ISP b0, DPM b5, ...) | K |
| `CLKGATECTLOVR` | the `CLKGATECTL` layout | the SGX545's own layout | K |
| Automatic clock gating | yes (`SGX_FEATURE_AUTOCLOCKGATING`) | yes | K |

The SGX545's status bits match what we measured with regsample (b0-1 the 3D side, b5 the
DPM). The SGX530's coarser status means its busy split works per unit: TA (b12), ISP and
TSP (the 3D side), DPM, USE and 2D, with no separate texture, PBE or PDS bits. The
`tools/state/busysplit.py` groups need an SGX530 table (D).

## Reset

`SOFT_RESET` at 0x0080 (K):

| Bit | SGX530 | SGX545 |
|---|---|---|
| 0 | BIF | BIF |
| 1 | 2D | DPM |
| 2 | DPM | TA |
| 3 | TA | USE |
| 4 | USE | ISP |
| 5 | ISP | TSP |
| 6 | TSP | (more units above) |

Every unit above the BIF moves up a bit, because the 2D reset takes bit 1.

## Events and kicks

- `EVENT_STATUS` keeps the SGX545's bit positions for every event the two share: master
  interrupt b31, timer b29, TA DPM fault b28, the DPM out-of-memory events (global b2,
  macrotile b1, ZLS b25), DPM state and control store/load/clear (b4-9), DPM memory free
  (TA b24, 3D b0), memory threshold b3, TA finished b13, TA terminate b12, TPC flush b10,
  TPC clear b11, ISP end tile b23, pixel BE end render b18, visibility fail b16, software
  event b14, breakpoint b15 (K).
- Only on the SGX530: 2D complete b27, OTPM loaded b21 (on the SGX545, b21 is the ISP2 ZLS
  context-switch finish), ISP halt b17 (K).
- `EVENT_STATUS2` has only the DPM TA and 3D free-load events (b0, b1). The SGX545's
  triggers, VDM context, GSG, MTE, DCU and OTPM events there are absent (K).
- `EVENT_KICKER` takes a 28-bit address (b4-27); the SGX545's takes 32 bits (K).
- **One kick register.** The SGX530 has no `SGX_FEATURE_MULTI_EVENT_KICK`, and
  `FIX_HW_BRN_22934` removes it from any core whose errata list it (K). Only `EVENT_KICK`
  at 0x0ac8 exists (`NOW` b0).

## The BIF and the MMU

| Fact | SGX530 | SGX545 | Tag |
|---|---|---|---|
| Device address space | 28 bits (256 MiB) | 32 bits | K |
| Memory contexts | one: `DIR_LIST_BASE0` only, no bank registers | 16 directory lists, per-requestor banks | K |
| `DIR_LIST_BASE0` address | b12-31, page-aligned | b8-31, with a 4-bit shift for 36-bit physical addresses | K |
| Page size | 4 KiB; no variable page sizes | 4 KiB to 4 MiB per directory entry | K |
| PDE, PTE address | b12-31: 4 KiB frames anywhere in 32-bit physical memory | b8-31 with the shift | K |
| PTE flags | valid b0, write-only b1, read-only b2, cache-consistent b3, EDM-protect b4 | the same | K |
| PDE flags | valid b0, write-only b1, read-only b2, cache-consistent b3, EDM-protect b4 | valid b0, page size b1-3 | K |
| `BIF_FAULT` address | b12-27 | b12-31 | K |
| Requestor bases (`TA`, `3D`, `ZLS`, `TWOD_REQ_BASE`) | b20-27: a 1 MiB-aligned base in the 28-bit space | b20-31 | K |
| `BIF_CTRL` bypass bits | cache b8, VDM b9, TE b10, 2D b11, PBE b12, TSPP b13, ISP b14, USE b15 | cache b8, VDM b9, TE b10, PBE b11, TSPP b12, ISP b13, USE b14, host b15 | K |
| `BIF_CTRL` low bits | no-reorder b0, pause b1, flush b2, `INVALDC` b3, clear fault b4 | the same | K |
| `BIF_INT_STAT` | fault b0-13, page-fault read/write b14 | other fields | K |
| `BIF_MEM_REQ_STAT` reads | b0-7 | b0-10 | K |

The PDE flags come from a DDK 1.4 header and differ from the later one we used for the
SGX545. The page-size bits of the later layout sit where the 1.4 header puts write-only and
read-only. Which layout the SGX530 silicon decodes is **U**; the safe first mapping sets
only the valid bit in the PDE, which both read the same.

**`FIX_HW_BRN_28889`** (K): when a command needs a data-cache invalidate and a BIF page
table or page directory invalidate together, the host first sends the microkernel a
command that does only the BIF invalidate, waits for it to report completion, and only then
sends the command with the data invalidate. The two must not be issued together.

## The USSE and its code base

- The SGX530 runs the USSE (first generation) instruction set, the same family as the
  SGX545 ([the porting README](../README.md); D).
- **2 USE pipes** (`SGX_FEATURE_NUM_USE_PIPES`), against the SGX545's 4 (K).
- The SGX545-only features `USE_NO_INSTRUCTION_PAIRING` and `USE_UNLIMITED_PHASES` aren't
  set for the SGX530 (K). What that means for encodings and scheduling is **U**: the
  feature names suggest that the SGX530 pairs instructions and limits the phases of a
  program, but nothing in the K sources defines either (G).
- `USE_CODE_BASE(n)`: the address field is b0-23 (24 bits) and the data master b24-25. On
  the SGX545 they're b0-24 and b25-26 (K). The address field's unit is **U** for the
  SGX530.
- F16 arithmetic, the C10 fixed-point format and the `efo` instruction are SGX545 facts in
  [ISA.md](../../ISA.md). Whether the SGX530 has each is **U**. No public source we may use
  says.

## Other features

From `sgxfeaturedefs.h` (K). Set for the SGX545 and not for the SGX530:
- volume textures;
- the texture-stride extension;
- host allocation from the DPM;
- `PDS_DATA_INTERLEAVE_2DWORDS`, and 2 PDS pipes;
- the monolithic microkernel;
- external Z for the ZLS;
- native backward blits;
- 512 TA render targets (`MAX_TA_RENDER_TARGETS`);
- secondary programs requiring a USE kick;
- the write-back DCU;
- `BIF_WIDE_TILING_AND_4K_ADDRESS`;
- the full-range vertex PDS address in the EDM.

Set for the SGX530: the 28-bit address space, automatic clock gating, an MP core count of
1, and the 2D unit's registers and events above. `SGX_FEATURE_2D_HARDWARE` is the name the
later cores use for their 2D unit; the SGX530's feature block doesn't set it, though its
register header has a 2D block. Whether its 2D unit is useful to us is **U**.

## The OMAP glue

| Fact | Value | Tag |
|---|---|---|
| Interconnect module | `target-module@50000000`, `"ti,sysc-omap4", "ti,sysc"` | L |
| Module registers | `rev` at 0x5000fe00, `sysc` at 0x5000fe10 | L |
| Sysconfig | an OMAP4-type layout with only the standby (`midle`) and idle (`sidle`) fields; force, no and smart idle for each. The OMAP34xx uses the OMAP2 type. | L |
| Module revision | ti-sysc's quirk table matches 0x40000000 at `rev` and applies the SGX quirk | L |
| SGX quirk | on module enable, ti-sysc writes bit 31 (`THALIA_INT_BYPASS`) of `OCP_DEBUG_CONFIG` at module offset 0xff08, to bypass the OCP interrupt logic. Without it, the GPU's interrupt doesn't reach the CPU (G, from the quirk's comment) | L |
| GPU node | `gpu@0` in the module: register window 0x50000000, 32 MiB | L |
| Interrupt | 21 on the OMAP3 interrupt controller at 0x48200000 | L |
| Functional clock `sgx_fck` | a composite: gate bit 1 at CM offset 0xb00, mux at CM offset 0xb40, with 8 parents (`core_ck` divided by 3, 4, 6 or 2, `cm_96m_fck`, `omap_192m_alwon_fck`, `corex2` divided by 3 or 5). The CM is at 0x48004000. | L |
| Interface clock `sgx_ick` | a wait-gate, bit 0 at CM offset 0xb10, from `l3_ick` | L |
| Which `sgx_fck` parent is chosen | not set in the DT: whatever the boot loader or the clock framework leaves | U |
| Clock domain | `sgx_clkdm`, hardware- and software-supervised, in `sgx_pwrdm` | L |
| Power domain | `sgx_pwrdm`: off or on, logic retention, one memory bank, the core voltage domain | L |
| Who manages them | the binding forbids `clocks` and `power-domains` on the GPU node for TI parts: the parent ti-sysc module enables both | L |
| Reset line | none in the DT | L; whether one exists is U |
| SoC variants without the GPU | AM3703, DM3725 and OMAP3611: ti-sysc disables the module at 0x50000000 | L |

The `50000000.gpu` platform device exists on our OMAP3630 test board with no driver bound, so its SoC
isn't one of the variants without the GPU (D).

The SGX545 is a PCI function: BAR registers, MSI, PCI power states. The SGX530 is a
platform device behind ti-sysc, so the driver's runtime PM goes through the parent module
(pm_runtime on the GPU device powers the module up and applies the quirk). When
`sgx_pwrdm` turns off, the GPU loses all state (D): the driver must reload the microkernel
and the BIF setup on every power-up, as it does after recovery.

## What this means for the stack

The kernel driver's core check (`pvrsgx_core.c`) requires `MULTIPLE_MEM_CONTEXTS`,
`MULTI_EVENT_KICK`, a 32-bit address space and at least two directory lists. The SGX530
meets none of them (D from K). An SGX530 entry is therefore more than a table row:
- **One memory context.** Each job's page directory goes into `DIR_LIST_BASE0`, with a BIF
  flush and `INVALDC` on every switch between VMs, following BRN_28889's ordering. Our
  per-requestor bank scheme ([UKERNEL.md](../../UKERNEL.md)) doesn't apply.
- **One kick.** The microkernel start that uses the SGX545's second kick needs another path
  through `EVENT_KICK` and the host-control words.
- **256 MiB of device address space.** The fixed layout in `pvrsgx_fw.h` assumes 32 bits;
  the SGX530 needs its own, smaller one.
- **The register offsets above** go into the family's `regs` table: clock status, core ID,
  revision, `PDS_INV3`, and the field shifts of `BIF_CTRL`, `SOFT_RESET` and
  `USE_CODE_BASE`.
- **The microkernel**: the open microkernel's register tables, the reset bits, the clock
  status and the PDS and USE code bases change. Whether it runs on the SGX530's USSE
  without changes is the ISA question.

## The TA stream (2026-11-15 to 11-27, open microkernel, parked)

Black-box work on an OMAP3630 board with our own frames (`tools/gen/sgxgen.c` knobs), the
open microkernel `sgx530_inv23` and only registers named in our docs. The details and every
run are in [the build log](../../log/entries/2026-11-19-2145-sgx530-pointer-mode-trace.md)
and [its predecessor](../../log/entries/2026-11-15-2245-sgx530-sgx535-ta-sequence.md).
**C** is confirmed on the board, **G** is a guess that fits.

**What a TA stream needs on this core.** With all of these, every program in the stream
runs and nothing faults:
- `0xa74` = 0x05208200 (b22-27 nonzero). Without it, the PDS holds every MTE-bound task (C).
- **Every MTE-bound update hands the MTE addresses, not words** (C). The MTE dereferences
  the state task's output words **o0 and o6** and no others (o1-o5 and o7-o15 tested). At o6
  it reads more than 4 and at most 16 bytes. This covers the state updates, the
  pre-terminate and the terminate. An update whose task emits nothing gives o0 = 0 and a
  read at absolute 0, so the stream has no empty secondary update.
  (`SGXGEN_STATE_PTR`, `SGXGEN_END_PTR`, `SGXGEN_END_NOEMPTY`)
- **State tasks end with one `emit.t1`** (C). Emit targets **t2 and t3 start a PDS fetch at
  their operand**: the SGX545's `emit.t3` ending reads `PDS_EXEC_BASE` + 0. t0 and t1 go to
  the MTE. (`SGXGEN_EMIT530=state1`)
- DOUTU word 0 b4 is code-address bit 15 (C; [PDS.md](../../PDS.md)).
- A VDM word of block type 0 is an address in 4-byte units that the VDM fetches from
  (requestor b4), so probably a stream link (G).
- `0x668` (the SGX545's PDS threshold) reads back 0 after a write: no register there (C).

**Where it stops.** The TA never ends, and there's no fault. `EVENT_STATUS` b12/b13 (TA
terminate and finished, at the SGX545's positions) never set, and no region headers or tail
pointers are written. The DPM never hands out a page: its documented registers are the same
at the hang for every stream. **A stream holding only the VDM end word (0xc0000000)
hangs the same way** (C), so the end of the pass isn't decided by the stream.

**Ruled out as what ends the pass** (each C, no change):
- the terminate record's header (0x2000 and 11 others, Rogue's `pres_terminate` b25
  among them) and its last-tile word (6 values, Rogue's TERMINATE0/1 forms among them);
- the terminate task's final emit: targets t0/t1, flags f10/f12/f13, n = 1-4;
- the terminate's VDM info word (bits 8-17 one at a time), the end word's b0, and leaving out
  the terminate program;
- the MTE's input words o1-o5 and o7-o11;
- the clear's record, its PDS words, and a draw or none;
- the free list's first page (`probe_pb_skip`).

**The kick itself (2026-11-20, also ruled out).** Compared with our own SGX545
microkernel's kick, on the fault-free end-only stream:
- The microkernel side is healthy (C): no bounded wait times out, the TA-in-flight flag is
  set, and it waits for `EVENT_STATUS` b13. The TA's clock stays on through the hang.
- Every register the kick writes from the SGX545's TA tables exists on this core and holds
  its value (C). The SGX545's forms of the TE tiles, screen packing, TE AA and VDM control
  (`ta_revert`), and each of 0xa74 bits 3-26, change nothing.
- **A read sweep of the whole register window** (approved for this board; through the
  driver's `probe_read`, only while powered, the 2D FIFO pair skipped) at idle and in the
  hang. The only values the kick doesn't set are:
  - read-only 0x228/0x22c = 0x1ff (written by the host or by the microkernel after its TA
    soft reset, they still read 0x1ff);
  - defaults 0x040 = 0x1e00, 0x100 = 3, 0x348 = 1, 0x4ec = 3, 0x614 = 0x2000,
    0x644 = 0x3db8, 0x738 = 1 and 0xaa4/0xaa8 = 0xaaaaaaaa;
  - **`EVENT_STATUS2` b4**, a one-shot event at every TA start (the SGX545's list doesn't
    name it). Cleared from the host mid-run, it stays clear and the TA still doesn't finish.
- 0x334 / 0x338 hold the last VDM index block's address and index count. With a draw the
  VDM gets past it and issues the terminate (the PDS PC is on it).
- **Microkernel variants** (scratch builds from the sgx530 branch's source, byte-identical
  to `sgx530_inv23` when unmodified), one step each: no TA soft reset, no free-list load,
  no DPM state/control load, no TA-side invalidates, OTPM clear value 1 (not 9), `TA_KICK`
  written twice, or with 3, 5 or 9. All hang the same way.

**Parked (2026-11-20).** With our own code, the SGX530's TA runs any stream to its
terminate and never raises TA finished. Nothing in the stream, the kick's registers and
order, or the readable register window changes that. What's left needs new information:
which register or protocol step this core's TA needs at the end of a pass that the SGX545
doesn't. The tools are in place: `probe_read`, `probe_init`, `probe_va0`, `probe_pb_skip`,
the sgxgen knobs above, and the microkernel's bring-up switches `UK530_POKE`, `UK530_VAR`
and `UK530_KICKVAL` (`ukernel/ukernel.py` on the sgx530 branch, 1b0f4c5a; all off by
default, and the default image is unchanged).

### Observed on the stock stack (2026-11-20)

With Joseph's approval, the stock stack was run on an OMAP3630 board and only observed:
our kernel and the GPL kernel module, the stock user space loaded into RAM at run time, and
a 64×64 render that reads back correctly. Our own sampler read the SGX register window
through `/dev/mem` while the GPU's ti-sysc module was held on by runtime PM. It recorded each
register's value before the render and every change during it. Nothing from the stock
stack's code was read or kept. Tagged **O** (observed on the stock stack).

**At the TA kick** (one sample, under 0.4 ms) the stock run leaves:
- the same TE and VDM layout as ours: 0x208/0x20c 0x01004004, 0x210 0x3003, 0x214 0x10,
  0x218 0x01000000 (0x01400000 later), 0x23c 0x1a2, 0x240/0x244 1e-6, 0x248 0x0003f03f
  (O). Ours already writes these.
- **0x614 = 0x27**, from a reset value of 0x2000. 0x27 is the stock PB descriptor's PDS
  threshold, so 0x614 is probably where this core keeps it. The SGX545's 0x668 isn't a
  register here (O for the value, G for the meaning).
- 0x250 = 0x88, 0x630 = 5, 0xa74 = 0x083f8200 (b27 set during the TA) (O).
- 0x26c = 0x44a, and later 0x308/0x30c once each. These are written by the hardware: writes
  to 0x26c don't stick (O; G: TA status and end-of-pass values).
- **The 3D free list (0x600/0x604/0x64c) is loaded together with the TA's**, and the 3D-side
  DPM words (0x70c/0x71c/0x728/0x730) track the TA-side ones (O).
- **The DPM hands out pages straight away:** 0x724 = 0x00020002, 0x72c = 0x00010001, and the
  head moves by two (O).
- 0x230/0x234/0x62c/0x634 are left at 0. The SGX545's tables write them (O).

**At idle, after the stock init:** 0xabc = 0x40, 0xb30 = 0x100, 0x040 = 0x1ff,
0x804 = 0x1000ffff, 0xa00 = 0x7c000, 0xa58 = 0x2204f00f, `CLKGATECTL` 0x00222220. The
`USE_CODE_BASE` entries are 0x800 apart, where ours are 0x80 apart (O).

**Applied to ours (C, no change).** Each of these was tried on the fault-free end-only
stream and with the clear's draw, through scratch microkernel images that write the values just
before `TA_KICK` (a `UK530_POKE2` switch in the scratch copy) or `probe_init` for the idle
values:
- 0x614 = 0x27;
- with 0x250, 0x274;
- with 0x230/0x234/0x62c/0x634 = 0;
- with 0xa74 = 0x083f8200;
- with 0x630 = 5 and 0x218 = 0x01400000;
- with the 3D free list loaded at TA time;
- the idle values 0xabc, 0xb30, 0x040, `CLKGATECTL`, 0xa00.

Every write that sticks holds its value, and the TA still hangs without asking the DPM for a
page.

**What a stock TA leaves in memory (O).** Read back through the GPU's page tables (two
levels, 4 KiB pages, as our driver builds them) while the render's context was still alive.
64×64 target, 16×16 tiles:
- **Region headers** (the TA's 0x21c), one 12-byte entry per tile in row order:
  - word 0 is the tile's position, x/8 in b16+ and y/8 in b0-15 (0x00020000 is the tile at
    x = 16), with b31 on the last entry and b28 with it (0x90060006);
  - word 1 is the tile's control stream as an offset into the PB, 0x1000 + 0x40 × tile;
  - word 2 is 0.
  The 3D's final region array (0x408) has entries of the form 0x10000000 | tile × 0x1000,
  with b31 on the last.
- **Per-tile control streams** (PB page 1, where the region headers point): a list of
  two-word entries, 0x44??ffff and the dword offset in the PB of an object block, ended by
  0xc0000000. Three entries in tiles the triangle reaches (offsets 0x09, 0x1c, 0x2d), two
  elsewhere.
- **Object blocks** (PB page 0), at those offsets: the state's ISP words first (ISPA,
  then ISPB when ISPA b9 is set: 0x01d00200, 0x000000f0), then 0x46124612 and 0x00000042,
  then the vertex positions. The words just before hold the vertex attributes (1.0 and the
  clear colour per vertex).
- The DPM pages start at the PB's base (`BIF_TA_REQ_BASE`): page 0 objects, page 1 control
  streams.

So the stock MTE gets the state block's words **as data** and copies them into the objects
it writes. Ours takes the state task's first output word as an address and never writes an
object.

**One bounded sweep (2026-11-20, C).** Sixteen of our own state-task forms, with an object in
our parameter buffer as the detector: data mode (the state block DMA'd in) with each of the
one-emit, three-emit and SGX545 task endings; the final emit's target, flags and n; the DMA's
form; DOUTU bit 21 and word 2; the VDM info form; and two pointer-mode controls. None wrote an
object. In data mode the MTE reads the header as an address every time.

**A state task with no o-bank write (C, 2026-11-27).** Emitting the DMA'd words from pa0
(`emit.t1 pa0, #n, #0`, `SGXGEN_EMIT530=statep`) makes the MTE read at address 0: it takes
the task's o0 as the block's address whatever the emit names
([log](../../log/entries/2026-11-27-0540-sgx530-ta-state-from-pa.md)).

**Write-only registers and the stock init script (C and L, 2026-11-27;
[log](../../log/entries/2026-11-27-0430-sgx530-ta-write-only-and-init-script.md)).**
- 0x42c = 0, as the stock transfer writes it, changes nothing on the TA kick or the transfer.
- The stock init script's 35 register writes (L) match ours, are layout, or were tried, except
  0x804 = 0xffff. Set at init, our microkernel never takes the kick (cache enables, G). Set just
  before `TA_KICK` (0x1000ffff, the stock's idle value), the TA still hangs.
- Parked again: what's left is the stock microkernel's TA-start sequence, which only its code
  shows.

**The DPM init and the SGX535's TA start (C and L, 2026-11-27;
[log](../../log/entries/2026-11-27-0600-sgx530-ti-header-dpm-init-once.md)).**
- TI's header (L): DPM page numbers are 14 bits here. The PDS page threshold is 0x614, not
  the SGX545's 0x668, and neither 0x664 nor 0x668 exists. `EVENT_STATUS2` has only the TA
  and 3D free-list loads. 0x6a8 is `DPM_TA_EVM` (INIT, done at `EVENT_STATUS` b22). 0x200
  is `VDM_START`.
- On the board, from fresh boots (C), none of these changes the TA hang (TA triggered, no
  page request, 0x734 = 0):
  - INIT once after the TA list load, in img-sgx's order;
  - the PDS threshold at 0x614;
  - 0x218 = `COMPLETEONTERMINATE` alone;
  - the TA-side `PDS_INV1` invalidate.
- Value mode still faults at the state header's value.

**TI's VDM, TE and MTE registers (L and C, 2026-11-27;
[log](../../log/entries/2026-11-27-0700-sgx530-vdm-te-registers-at-the-hang.md)).**
- Header facts (L):
  - 0xa74 is `DMS_CTRL`. Its b22-27 gate is the maximum vertex (b25-27) and pixel (b22-24)
    partitions.
  - 0x230/0x234 are OTPM control-stream bases, and 0x62c/0x634 the DPM state and control
    table bases. 0x250 holds the MTE's sample positions.
  - Our TE table also writes 0x2a8-0x2d4, 0x324, 0x364-0x374 and 0x74c, which the SGX530
    doesn't name.
- The PB load now writes the PDS threshold to 0x614, without 0x664/0x668 (sgx530 branch
  ce7a1b60, C: null).
- At the hang (C), the VDM has read only the first block (0x334 = base + 8), and the MTE
  signatures stay 0.
- The TE table cut to the named registers, with the RT flags in 0x250, hangs the same.

**The SGX535 driver's stream and state task (L and C, 2026-11-27; parked;
[log](../../log/entries/2026-11-27-0800-sgx530-ta-img-sgx-stream-parked.md)).**
- img-sgx's state update, state PDS program, state task, draw and end of stream match
  ours or an existing sgxgen knob, word for word. Its task is our `state_emit_<n>_530s`.
  The only word with no knob is b31 of its state DMA control, which the 530 stock leaves
  clear.
- In that form, pointer mode hangs after the first block and value mode faults at the
  header's value (C).
- The TA is parked until the SGX530's emit forms or a stock state task's MTE input are
  known.

**What this narrows it to.** The stock TA allocates parameter-buffer pages as soon as it runs,
and ours never does, even with the stock register state. So the difference is upstream of the
DPM and the kick's registers: what the MTE receives from the state tasks. On this core the
state task's first output word reaches the MTE as an address. The stock task's way of handing
over the state is in its USSE code, which observation-only work doesn't read.

## 3D only (2026-11-26, a transfer)

A transfer is a render with no TA: one background object covers the destination, and its
pixel program and end-of-tile program do the rest. On the SGX545 it renders on dev, so it's
the way to the 530's first pixels without the TA. Details and every run:
[the build log](../../log/entries/2026-11-26-1000-sgx530-3d-only-transfer.md). Our own code
only: powervr_sgx, the sgx530 branch's microkernel and `powervr_sgx_blit -c` (a clear).

- **The 3D starts.** `k_transfer`'s registers (the SGX545's `T3_CMD` table) each hold their
  value, the `0x428` kick starts the 3D, and `CLKGATESTATUS` shows ISP b4 and TSP b8 on
  (0x00110110). 0x42c, written 0x80000000, reads 0. (C)
- **The 3D-side invalidate-done mask is 0x45**: PDS_INV1 b2+b6 and the CSC b0. The SGX545's
  0x4b times out here. (C)
- The client side on this core: 8-word PDS data, DOUTU offsets in bytes, 16-pixel tiles, and
  the pixel-event PDS address (0xa5c) as an offset from `PDS_EXEC_BASE`. The stock 3D's 0xa5c
  is 0x14000 under an exec base of 0x0dc00000 (O). The driver sends it that way
  (`PVRSGX_FEATURE_PDS_EVENT_OFFSET`). The 3D never reached a pixel event, so the form is O,
  not C.
- **Where it stops.** The pass reads 0x0f00f000 (requestor b1), a hole in the kernel data
  heap. With a page mapped there (nothing is written to it), it next reads 0x0b860000
  (requestor b6) in the 3D parameters heap. The 3D-end event never comes. The destination,
  the background block's address, the tile count, the end-of-tile and emit tasks and the
  page's contents move neither address. No register in our full-window sweep holds either.
  (C for the reads; where the 3D gets the addresses is U.)
- **The stock 3D (O, a render, 2026-11-20 samples).** It writes the SGX545 render's 3D
  registers with the SGX545 render's constants: 0x400 0x80, 0x414 0xf0000, 0x4bc 0x300,
  0x418 1, 0x63c 3, 0x404 0, 0x408 its region array. Two values differ from the SGX545's:
  0xa64 = 0x4ffe (the SGX545's 1), and 0x48c/0x490 = 0x80000000. Writing 0x48c/0x490 once at
  init doesn't move the first read (C). No stock transfer was observed.

**The stock transfer (O, 2026-11-26; [the log](../../log/entries/2026-11-26-2015-sgx530-stock-transfer.md)).**
A `glTexImage2D` and a `glCopyTexImage2D` each ran one. They wrote the same registers as
`k_transfer` with the same values: 0x404 3, 0x408 0, 0x410 0x00030003, 0x414 0x100, 0x4bc
0x200, 0x63c 0. They differ in:
- the bases: 3D_REQ_BASE 0, the background block at 0x22000 (0x4c4 0x02002200), and the pixel
  event at the PDS exec base + 0 (0xa5c 0);
- 0x4d4 / 0x4d8 / 0x4e4 = 0x31db3dc7 / 0x2341b117 / 0x303 at the end. **The 3D writes these
  three itself (C):** values written from the host before our transfer read back as
  0xcf93eb13 / 0x24f486cc / 0x202 at our fault, the same in every run. Ours stops with
  0x4e4 0x202 where the stock ends with 0x303 (progress fields: G).

On ours (C): the stock's 0x4d4/0x4d8/0x4e4, 0x630 = 2 and the render values it inherits
(0x418-0x424, 0x48c/0x490), each written at init, and the pixel event at exec base + 0, all
leave the fault at 0x0f00f000. Only the low address layout (3D_REQ_BASE 0) is untried.

**First pixels (C, 2026-11-27; [the log](../../log/entries/2026-11-27-0200-sgx530-first-pixels-stores.md)).**
The clear transfer's pixel program can store to memory. `st.a.d` from the background object's
pixel task writes 32×32 pixels of the destination with the clear colour, and the client reads
back 1024/1024 right. The recipe for another core is [first-output.md](../first-output.md).
- **The fixed reads were ours.** 0x0f00f000 is the clear colour 0xff00ff00, masked to 28 bits:
  a pixel task's `limm o0, #c [end]` gets o0 read as an address by requestor b1, as the TA's MTE
  reads its state task's o0.
- **Requestor b6 is the PBE.** It writes the tile (the colour with its bytes reversed) as 16
  runs of 8 words, 0x8d70 apart, from 0x0b85741c, then faults at 0x0f000000. Nothing in the
  end-of-tile task we write moves those addresses: its emit words, sideband, registers (r, o,
  pa), temporaries, the launch from the pixel event program. The PBE path is open.
- `imae` multiplies 16-bit sources and adds a 32-bit one. A store's offset reaches #127 dwords.
- **A full 64×64 clear (C, [log](../../log/entries/2026-11-27-0400-sgx530-full-clear-branches.md)):**
  a store loop with a `(p0) br` back-edge writes all 4096 pixels.
  - `br` counts from the branch, in instructions.
  - A program that branches needs a code object of its own: inline after other programs, a
    taken branch hangs the task (cause unknown).
  - A pixel task launched by our background PDS program has r0-r3 only. DOUTU word 0 b24-31
    doesn't change that (open).

**The stock transfer command and 0xa64 (O and C, 2026-11-27;
[log](../../log/entries/2026-11-27-0500-sgx530-stock-transfer-command-0xa64.md)).**
- The stock command's 17 3D words equal ours except 3D_REQ_BASE (0), 0x42c (0, ours
  0x80000000) and 0xa64 (**0x4ffe**, ours 1) (O).
- With 0xa64 = 0x4ffe the end-of-tile task's registers work: its store lands. With 1 they
  don't, which is why its emits sent stale values (C).
- Our PBE emits then write nothing, in the SGX545 or the SGX535 word order: the PBE emit is
  open (C).
- A pixel task's register 0, in any bank (r, o, pa, 3, 4, 7), is what reaches the tile. Only
  the o bank is also read as an address (requestor b1), as the TA's MTE reads its state task's
  o0 (C).

**The PBE writes a tile (C and L, 2026-11-27;
[log](../../log/entries/2026-11-27-0900-sgx530-pbe-writes-a-tile.md)).**
- The event program's DOUTU word 2 for the end-of-tile task needs b28. That's the SGX535's
  form (L, img-sgx). The SGX545's b23 stops the write.
- With 0xa64 = 0x4ffe, the PBE then writes one full 16×16 tile of the clear colour at the
  destination, at the right pitch. The words for that:
  - r0: (pitch / 2 − 1), the emits' third operand;
  - r1: (h − 1) << 12 | (w − 1);
  - r2: 0x8000;
  - r3: the address;
  - the sideband: 0x204.
- The tile word is the SGX535's (C, each tile on its own):
  - b28 enables the write;
  - x from in0 b0-7 lands at b11-18, y from in0 b9-15 at b20-26.
- With img-sgx's emit form, a clear that writes r0 needs no mapped page.
- Each job still writes only one tile: `PIXELBE_EMIT` stays 3 and no end-of-render event
  comes ([log](../../log/entries/2026-11-27-1000-sgx530-pbe-tile-word-one-tile-per-job.md)).
- b27 in the tile word is the end of render (C): set, the job completes. A stock 1024²
  upload advances one tile per ~2.6 µs and raises the PBE's end of render (b18) once,
  after the last tile (O). On ours the 3D issues one end-of-tile event per render after a
  plain pixel task. Parked ([log](../../log/entries/2026-11-27-1300-sgx530-big-stock-transfer-end-of-render.md)).
- After the first end-of-tile task, no event task of any kind runs: the timer and end-of-render
  events stay pending, unhandled (C, [log](../../log/entries/2026-11-27-1400-sgx530-event-tasks-stop-after-one-end-of-tile.md)).

A host-built parameter buffer (region array, control streams, object blocks) goes through the
same 3D, so these reads would likely stop it the same way. It wasn't tried.
