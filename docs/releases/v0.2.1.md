A bug-fix release of the open graphics stack for the PowerVR SGX545 in Intel's Cedarview
Atoms (N2600, N2800, D2500, D2550, D2700) and the Intel Atom CE5300. It fixes the screen
flicker on Cedarview, a black desktop on DKMS installs, and the games testers reported on
0.2.0. Thanks to everyone who tested 0.2.0 and sent logs, screenshots and traces.

**Upgrade the kernel, the firmware and Mesa together, then restart.** The interface between
the kernel driver and Mesa is the same as 0.2.0's, so 0.2.1's Mesa also runs on the 0.2.0
kernel, but the Cedarview fixes are in the kernel.

## What's fixed

- **Cedarview: the screen jumping sideways.** On some machines a band of the screen showed
  shifted for one frame, most often on an idle desktop. A CPU in its deep C4 state woke too
  slowly for the display's FIFO. The kernel driver now holds the CPU's wake-up latency to
  50 µs while the GPU has work, and lets go 100 ms after the last job, so an idle desktop
  still reaches its deep C-states. Found, traced and tested by danilolc, and confirmed on
  a second machine by WastoLord.
- **A black desktop on DKMS installs with a stock kernel** (Cedarview). Built by DKMS against
  a kernel without this project's patches, the driver mapped every buffer to nothing, so X
  drew a black screen with a GPU fault per buffer. Found and fixed by danilolc.
- **Games:**
  - **OpenArena (and ioquake3) with `cl_renderer opengl2`:** a black screen in 0.2.0 unless
    started with `+set r_ext_framebuffer_object 0`. Copying an offscreen image to the window
    read the same pixel for the whole screen. This was any copy of an offscreen image to the
    window through `glBlitFramebuffer`, not only OpenArena's. Its post-processing shaders,
    which were refused ("too many dependent texture samples"), compile now, and copies
    between its offscreen images run on the GPU instead of the CPU: about 7 to 12 FPS on
    oa_dm1 at 640x480 on a CE5300 board. `opengl2` is still a heavy renderer for this GPU,
    and `opengl1` stays the faster choice.
  - **Geometry Dash, the "Dash" level** went black when its effects started. The effects
    shader reads the screen more than 60 times, more than the driver allowed, so it didn't
    compile. A program may now make up to 256 texture reads.
  - **GTA Vice City under Wine:** `GL_INVALID_VALUE in glTexImage3D(level=0)` at start-up.
    The driver had no 3D textures at all, and Wine makes small ones for every texture unit.
    3D textures of one texel work now. Wine shows its frames through the same kind of copy
    as OpenArena, so the black screen is likely fixed too, but Wine hasn't been tried on a
    board.
  - **Games that upload their vertices with `glBufferData` before every draw** (such as the
    Super Mario 64 PC port): when a busy frame filled up in the middle of a draw, the driver
    could free a buffer's GPU copy one frame too early, so the GPU read another draw's
    vertices, and in some scenes hung. Small buffers also share a few GPU allocations now,
    instead of one each, which takes most of the CPU time such games spent in the kernel.
    If a game misbehaves after this, `SGX_DEBUG=novboslabs` turns the shared allocations
    off, to tell the two changes apart. Reported and traced by danilolc.
- **Debugging:** `SGX_DEBUG=draw` now says why a draw was dropped.

## Upgrading

**From 0.2.0, with the apt repository:**

```bash
sudo apt update && sudo apt upgrade
```

Then restart. With the 32-bit package (`mesa-sgx:i386`), `apt upgrade` updates it too.

**From 0.1.x or from test builds:** see the 0.2.0 notes, "Upgrading", and install 0.2.1
instead of 0.2.0.

**CE5300 (DKMS), and Cedarview with DKMS:** rebuild the driver from this release's source as
in docs/INSTALL.md, section 2.

## Tested

On CE5300 boards with the 0.2 kernel and its open microkernel, and this release's Mesa
(2026-11-14):

- **dEQP-GLES2**, the whole mustpass list: the same results as before these changes, test
  for test (16,637 pass, 78 expected failures).
- **piglit**, the GL 2.1 list and the 3D-texture, blit and copy tests (336), against 0.2.0's
  Mesa: no new failures. `tex3d-maxsize` now crashes in the test itself, which divides by
  zero when the largest 3D texture is one texel.
- **A test of these fixes** (`mesa/tests/sgx_gamefix`): 16 and 24 texture reads a pixel,
  one-texel 3D textures, 1,024 draws a frame from re-uploaded buffers, and copies of
  offscreen images. 0.2.0's Mesa fails the texture-read, 3D-texture and buffer parts (the
  last one drops whole draws); 0.2.1's passes every part.
- **OpenArena 0.8.8 with `cl_renderer opengl2`** under X: the menu and oa_dm1 draw with
  offscreen rendering on.

The Cedarview fixes were tested by danilolc and WastoLord on their own machines.

## Known issues

- **No OpenGL 3.x or OpenGL ES 3.0 yet.** The driver offers OpenGL 2.1 and OpenGL ES 2.0.
- **3D textures** larger than one texel aren't supported yet.
- **Portal and other Source games** need `glColorMaskIndexedEXT` (`GL_EXT_draw_buffers2`),
  which the driver doesn't have yet.
- **ioquake3's `opengl1` renderer** can leave a map's world undrawn on a CE5300 board;
  this is being investigated.
- **sRGB textures** are decoded in the shader. Filtering across mipmap levels and sRGB
  border colors aren't right yet.
- **The Cedarview desktop** is still slower than it should be.
- **The same as 0.2.0:**
  - `perf record` with precise events (PEBS) can corrupt memory on these Atoms; use
    `perf record -e cpu-clock`.
  - Some Cedarview panels stay dark with `gma500`, with Debian's kernel too.
  - CE5300 boards have no kernel package (DKMS only).

## Installing

New installs: docs/INSTALL.md. Check the downloads with `sha256sum -c SHA256SUMS`.

Please report problems on the issue tracker, with your computer model and the output of
`sudo dmesg | grep -i -E 'powervr|gma500|drm'` and `glxinfo -B`.
