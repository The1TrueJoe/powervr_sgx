# Vertex constants: an indexed array in memory was loaded into nowhere; the limit goes to 256 vec4

2026-11-19, a CE5300 board (the packaged powervr_sgx kernel, open microkernel v0.2.1), our Mesa
staged into the Debian root by hand, surfaceless EGL. Issue #5: Half-Life: Source Deathmatch on a
Cedarview (GL 2.1) ran with a black screen, and the log showed `vertexlit_and_unlit_generic_vs20`
and `_ps20b` failing to compile with no message. Direct3D 9's vs_2_0 has 256 float constants,
and games ported through a D3D9-to-GL layer declare their vertex constants as one vec4 array,
indexed by the vertex (skinning). We exposed 128 vec4 (GLES2's minimum). The cause in Source
itself is not confirmed yet; the reporter was asked for a `MESA_GLSL=errors` log.

**Probe:** `mesa/tests/sgx_vconst` declares `uniform vec4 vc[GL_MAX_VERTEX_UNIFORM_VECTORS]` and
draws each pixel of a 16x16 target with a quad that reads `vc[int(i)]` by an attribute straight
into a varying; then the same array with constant indices, a `mat4` bone array indexed by an
attribute, and one vec4 past the limit (must not link).

| build | limit | dynamic | constant | bones | past the limit |
|---|---|---|---|---|---|
| dev (A) | 128 | FAIL, 256 of 256 | PASS | FAIL | PASS |
| limit 256 only (B) | 256 | FAIL | PASS | FAIL | PASS |
| the fix (D) | 256 | PASS | PASS | PASS | PASS |

Every failing build printed `Unhandled #dst1 encode case: 0x0` from the encoder.

**Cause:** an indexed uniform array that doesn't fit in SA is read from the constant memory block
(`mem_index`: `imae` the address, `ld.a.d` each component). The load takes the indexed `mov`'s
destination as its own. `fold_movs` runs first and folds `mov o, w` into that `mov`, so for an
array read straight into a varying the destination is an output register. A load writes only a
temporary or PA (`#dst1`), so the encoder had no case for it and wrote r0: the varying was never
written. dEQP-GLES2 never reaches this path: its indexed arrays fit in SA.

**Fix:**
- `mem_index` loads into a temporary when the destination can't take a load, and moves it there after the `wdf`.
- `sgx_encode_ins` fails the compile on a load whose destination isn't a temporary or PA, instead of encoding r0.
- The vertex limit is 256 vec4 (plus the 9 st keeps). The memory block's windows (one per 128 words, `SGX_MAX_MEM_BASES`) went from 8 to 12, so every slot of the constant map has one: 256 vec4 of uniforms plus the driver's constants need a ninth.
- A compiler test: `vertex_indexed_memory_constants_to_varying`.

The old note in `sgx-fails.txt` said a 136-vec4 buffer broke `shaders.indexing.tmp_array`. With 265
vec4, `dEQP-GLES2.functional.shaders.indexing.*` passes 568 of 568, as dev does, and
`implementation_limits.*` passes 16 of 16, so the note was stale.

**No regressions** (dEQP-GLES2, pbuffer, rgba8888d24s8ms0), dev against the fix:

| group | dev | the fix |
|---|---|---|
| `functional.shaders.*` | 10196 pass, 3 fail, 53 not supported | the same, the same 3 |
| `functional.uniform_api.*` | 1124 pass, 143 not supported | the same |
| `functional.shaders.indexing.*` | 568 of 568 | 568 of 568 |
| `functional.implementation_limits.*` | 16 of 16 | 16 of 16 |

The 3 fails on both: `texture_functions.fragment.texture2dproj_vec4_bias` (in `sgx-fails.txt`) and
`scoping.valid.local_variable_hides_function_parameter_{vertex,fragment}` (not in it; not
looked at here).

**Also:** a drirc entry (`mesa/patches/0008`) gives ioquake3 and OpenArena
`force_glsl_extensions_warn`. Their ES renderer declares a `sampler2DShadow` precision without
enabling `GL_EXT_shadow_samplers`, and every shader failed. `sgx_glsl_prec` built as `ioquake3`
compiles the ioquake3 header; under its own name it still fails it, as before.
