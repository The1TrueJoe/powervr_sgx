# SGX530: a 3D-only render (a transfer) starts the 3D, which then reads fixed addresses and never ends

2026-11-26 09:58-10:31 UTC, an OMAP3630 board, kernel 7.3.3, RAM only (module load, one client
run, unload). Our own code throughout: the open microkernel, powervr_sgx and `powervr_sgx_blit`.
Every run recovered through the driver's reset. The board stayed on its normal SD boot.

## Why a transfer

The TA is parked: it never raises TA finished ([sgx530.md](../../porting/cores/sgx530.md), "The
TA stream"). A transfer is a render with no TA. One background object covers the destination,
its pixel program runs the shader, and the end-of-tile program writes the tile through the PBE
([UKERNEL.md](../../UKERNEL.md), "Transfer"; [TEX.md](../../TEX.md) section 3). The SGX545
renders this way on dev, so the transfer is the shortest path from the 530 to pixels in memory.

## What it took on the 530

- **The client** (`drm/tests/powervr_sgx_blit.c`, `tools/tex/sgxtex.c`). sgxtex takes the core
  from `sgxtex_set_core()`; the SGX545 default gives byte-identical words (`sgxtex_test`
  output compared). On an SGX530 the test sets:
  - 8-word PDS data blocks (`sgxtex_pds_layout`);
  - DOUTU offsets in bytes in a 32 KiB window, as DEV_QUERY reports;
  - 16-pixel-wide tiles;
  - PDS addresses from the device's PDS pixel heap.

  `-c` runs a clear: a background pixel program (DOUTU only, word 1 = 4) that starts
  `phas.i; limm o0, #0xff00ff00 [end]`.
- **The driver.** The 530's pixel-event PDS address goes to the 3D as an offset from
  `PDS_EXEC_BASE` (`PVRSGX_FEATURE_PDS_EVENT_OFFSET`). The stock stack's 3D has 0xa5c =
  0x14000 under an exec base of 0x0dc00000 (observed, 2026-11-20). The SGX545 takes the
  device address.
- **The microkernel.** The sgx530 branch's image (`sgx530_inv23`, rebuilt byte for byte from
  1b0f4c5a) already has the SGX545's transfer handler, `k_transfer`. It waits for the
  3D-side invalidate with the SGX545's done mask 0x4b, and on the 530 that wait timed out
  (bounded wait 7, control block +0xa0). PDS_INV1 sets b2+b6 here and the CSC b0, so the
  mask is 0x45. A scratch image with `INV_DONE_3D = 0x45` (6 bytes differ) times out nowhere.

## Runs

All with a 64×64 BGRA8888 destination unless noted. "Fault" is the job's first BIF fault.

|---|---|---|---|
| 1 | clear | inv23 | fault at **0x0f00f000**, requestor b1 (BIF status 0x4002); wait 7 timed out once |
| 2 | clear, destination +64 KiB (`-p 0x10000`) | 0x45 | the same fault; no wait times out |
| 3 | clear, end-of-tile program `nop [end]` (`-E`): no `emitpix` | 0x45 | the same |

| 5 | clear, background block +1 MiB (`-B 0x100000`): 3D_REQ_BASE 0x01900000 | 0x45 | the same |

| 7 | 2 with `probe_read` of the 3D registers | 0x45 | every transfer register holds its value (below) |
| 8 | 2 with `probe_read` 0xa00-0xa7c | 0x45 | the code bases and event PDS words as at init; nothing holds 0x0f00f000 |
| 9 | 2 with a page mapped at 0x0f00f000 (`probe_kpage`), word i = 0x0e900000 + 0x100 i | 0x45 | nothing written to the page; next fault at **0x0b860000**, requestor **b6** (0x4040) |

In every run:
- the 3D started: `CLKGATESTATUS` went from 0x00110000 to **0x00110110**, ISP b4 and TSP b8;
- the 3D-end event task never ran: the control block's per-event heartbeat stayed at 2 (init
  and the kick), and the transfer CCB's read offset stayed 0;
- the destination stayed all zeros, the done sync unwritten.

**The 3D registers at the fault (run 7):** 0x400 0x80, 0x404 3, 0x40c 0, 0x410 0x00030003,
0x414 0x100, 0x4b8 1.0, 0x4bc 0x200, 0x4c4 0x02000100, 0x4c8 0x88, 0xa5c 0x1040, 0xa64 1,
0xab8 0x0d800000, 0xcac 0x01800000, 0xa74 0x07e08200. 0x42c, written 0x80000000, reads 0.
0x418-0x424, 0x480-0x490, 0x148, 0x600-0x61c, 0x63c, 0x64c, 0x658 and 0x70c/0x71c read 0.

## What this says

- The 530's 3D takes the SGX545's transfer registers (each holds its value), starts on
  `0x428`, and clocks ISP and TSP. **C.**
- **The 3D-side invalidate-done mask is 0x45** (PDS_INV1 b2+b6, CSC b0). **C.**
- The pass reads 0x0f00f000 and, once that page exists, 0x0b860000. None of these moves the
  first address: the destination, the background block, the tile count, the end-of-tile
  and emit tasks. The page's contents don't move the second one. **C.**
- 0x0f00f000 is in the kernel data heap's hole between the firmware's data arena (to
  0x0f00e000) and the first kernel object (0x0f010000). 0x0b860000 is in the 3D parameters
  heap. No register in the 11-20 full-window sweep of our stack holds either value. So the
  3D builds them from state the transfer leaves unset, and every unset register reads 0
  (G).
- Requestor b1 is the one that took the TA's state output as an address (2026-11-15). b6 is
  new. Which units they are isn't known.

## Where it stops

The pass reads addresses that nothing we write moves. The next steps would need the 530's own
3D-only setup: which register or memory word the 3D takes those reads from. The stock stack's
3D was observed only for a render (0x404 = 0, a region array at 0x408), never a transfer.
For a render the stock values match the SGX545's render constants (0x400 0x80, 0x414
0xf0000, 0x4bc 0x300, 0x418 1, 0x63c 3). Two differ: 0xa64 = 0x4ffe (the SGX545's 1), and
0x48c/0x490 = 0x80000000. A host-built parameter buffer (the next step in the plan) goes
through the same 3D, and these fixed reads would most likely stop it the same way. It wasn't
tried. I stopped here rather than sweep 3D register values.

## Tools added (all off by default, SGX530 only)

- powervr_sgx: `probe_kpage=<addr>` maps a page in a firmware heap hole, word i =
  0x0e900000 + 0x100 i; with bit 0 of the address set, every word = `probe_kpage_fill`. The
  hang dump prints the words that changed (`PROBE_KPAGE`).
- `powervr_sgx_blit`: `-c` the clear only, `-p` bytes before the destination, `-B` bytes before
  the background block, `-w` the clear's width, `-E` / `-E -E` no end-of-tile emit / no emit
  task.
