# SGX530 board: the SGX535's host-driven TA sequence, applied one difference at a time

**2026-11-15 22:45 UTC onward. Our OMAP3630 test board, kernel 7.3.3, under lock. Each run
recovered by HWR; modules unloaded after each.**

## Where the lead comes from

The open SGX535 driver poulsback (MIT, public on GitHub) runs its GPU without a microkernel:
the kernel writes the TA and 3D registers itself, in action lists checked into its source
(`src/raster/sgx535_engine121.c`, `kernel/engine/poulsback_regtable.c`). The SGX535 is the
SGX530's closest relative. The GPL register headers of the two agree on every register both
name (36 of the 530's 36 offsets, same addresses), and its PDS invalidate-done bits in 0x138
(0x22 for `PDS_INV0`, CSC b0) are the ones we measured on the 530 on 2026-11-14. So its TA
sequence is the best public description of a TA start on this family that doesn't come from
the SGX545. Only its source code and its kernel execution doc were read, not its RE notes.
Every fact below is a lead (tag **L**) until the board confirms it.

What the SGX535 writes, against what our microkernel (SGX545 base) writes on the 530:

| | SGX535 (poulsback) | ours on the 530 |
|---|---|---|
| TE/MTE registers | 0x204, 0x208, 0x20c, 0x210, 0x214, 0x218, 0x21c, 0x220, 0x238, 0x23c, 0x240, 0x244, 0x248, 0x250, 0xc90 | the same, minus 0x250; plus 0x230, 0x2a8, 0x2b0-0x2d4, 0x324, 0x364-0x374, 0x74c, 0xa04, 0xaa0 (the SGX545's tail map) |
| 0x218 (TE_PSG) | 0x400000 (complete on terminate); **bit 24 never set** | cmd word \| 0x01000000 always |
| 0x250 | 0x88 | not written (the SGX545 puts 0x88 in 0x230) |
| tile, macrotile, screen words | same formulas as ours (16x16 tiles) | |
| PB / TA free list (0x618-0x668, 0x684) | same words, from the same descriptor fields | + 0x664 = 3 (the SGX545's selector) |
| before the kick | 0x65c = 0; 0x694 = 0x698 = 2; 0x24c = 1; 0x224 = 0x80000000; wait EVENT_STATUS 0x00100a40 | 0x694 = 0x698 = 2 (wait 0x240); 0x24c = 9 (wait b20) |
| at bring-up | all four DPM lists loaded (0x680/0x684/0x688/0x690), 0x6a8 = 1 (wait EVENT_STATUS b22) | TA list only |
| host init | 0xca0 = 0xc07c, 0x13c = 0, 0xa7c = 0, 0xa80 = 0, 0xa74 = 0x05188200, 0xa78 = 0, 0xaac = 0x44, 0xabc = 0xc, 0x804 = 0xffff, 0xa00 = 0x7c000, 0x630 = 0 | 0xa74 = 0x208200 only |
| 0xa74 | `DMS_CTRL`: b0-2 stop the PDS issuing vertex/pixel/event tasks | the SGX545's TA-flags field b27-31 |

**Confirmed on the 530 (C):** EVENT_STATUS b11 is the tail-pointer-cache done event for
0x224 = 0x80000000, and 0x6a8 = 1 raises EVENT_STATUS b22, as on the SGX535. So the SGX535's
TA/DPM register map holds on this core where we have tested it. The TE/MTE register values
and the DPM bring-up differences are not what keeps the MTE from becoming ready.

## 0xa74: the gate in front of the MTE (C)

On the SGX535, 0xa74 is the PDS data-master control (`DMS_CTRL`: b0 pauses DPM allocation,
b0-2 stop the PDS issuing vertex, pixel and event tasks), and its bring-up writes 0x05188200.
Ours writes 0x00208200 (the vendor's 530 default, 0x003f8200, was null on 2026-11-15).
`probe_a74=0x05188200`, same image and client as above:

| variant | result |
|---|---|
| base image, 0xa74 = 0x05188200 | **the TA-block state program runs**: PDS_PC moves on to 0x002004dc, then a BIF fault at **0x0000d000** (BIF_INT_STAT 0x4002, requestor b1); HWR, the fence signals in 23 ms; pixels 0 |
| the same, microkernel without the SGX545's TA-field OR into 0xa74 | the same |
| that microkernel, 0xa74 = 0x00208200 | the old stall at 0x0020048c |

0xa74 reads back 0x05188200 mid-job: bits 27-31, the SGX545's TA-flags field, don't latch
on the 530. So the PDS holds MTE-bound tasks while 0xa74's bits 16-26 are 0x020 (ours) or
0x03f (the vendor's 530 default); with the SGX535's 0x518 it issues them. The field layout is
**G**: 0x518 splits as 0x18 in b16-21 and 0x14 in b22-27, which would read as two per-data-
master task limits. The second one is 0 in both of the values that stall. Split on the board:

| 0xa74 | result |
|---|---|
| 0x05208200 (ours with b22-27 = 0x14) | runs, the same 0xd000 fault |
| 0x00188200 (ours with b16-21 = 0x18) | the old stall |

So **b22-27 of 0xa74 must be nonzero for the PDS to issue MTE-bound tasks on the 530 (C)**;
0x14 works. What the field counts is G.

The fault is the one the 0x16100 form gave on 2026-11-15 (the state header 0xd4c3, emitted
first, taken as an address). With the TA-block form admitted, the state task now runs and
its emitted words reach the MTE the wrong way. Next: the emit itself.

## With 0xa74 fixed: what the MTE does with the state task's output

Frame tool from `wip/sgx530-frame5` (sgx530-kick-frame CI), modules and image as above,
`probe_a74=0x05208200`. New knobs: `SGXGEN_CLEAR_ONLY` (the frame without the triangle),
`SGXGEN_EMIT530`, `SGXGEN_CLEAR_NOB15`, `SGXGEN_STATE_PTR[_ADD]`.

| variant | result |
|---|---|
| full frame, `SGXGEN_DUMP_PDS` | the PDS PC 0x002004dc is the triangle's state program (0x0e001340 + 0x30): the clear's state program and the clear's vertex fetch got through |
| `EMIT530` (the SGX535's one-phase emits), `STATE_PRIMARY`, BIF_3D_REQ_BASE = params base | the same 0xd000 fault |
| clear only | fault at 0x0000d000 (requestor b1), PDS at the terminate program |
| clear only, empty state task | fault at **0** |
| clear only, header 0x54c3 (`CLEAR_NOB15`) | fault at **0x00005000** |
| clear only, the task emits the block's address (`STATE_PTR`) | the b1 fault is gone; a new one at 0x0d800000, requestor **b2** |
| the same, address + 1 MiB | fault at **0x0e101000**, requestor b1 |

**On the SGX530 the MTE takes the state task's first emitted word as the address of the
state record and fetches the record itself (C).** The header-as-address faults (0xd4c3 →
0xd000, 0x54c3 → 0x5000, nothing emitted → 0) and the moved pointer (+1 MiB → the fault
moves +1 MiB) all fit it. The SGX535's driver emits the record words; the SGX530 does not
take them that way. With a good pointer the TA gets further and faults in the page under
`PDS_EXEC_BASE` (requestor b2); nothing reaches the region headers yet.

### Which word the MTE takes, and the next fault (all clear only, 0xa74 = 0x05208200)

`SGXGEN_EMIT530` swaps in one-phase twins of the state-emit and vertex programs (no
`phas.i`; `=state` or `=vs` for one side). The state twin keeps the SGX545's ending
(`emit.t3 r0`, `op0xd6`, `emit.t1 o0, #0, #0 [end f3_20]`) unless built with
`MKUSSE_530_EMIT535`, which ends it with the SGX535's `emit.t1 r0, #n, #0 [end f3_20]`.

| state task | vertex task | `STATE_PTR` | fault |
|---|---|---|---|
| SGX545 form (`phas.i` + three emits) | SGX545 | yes | 0x0d800000, b2 |
| SGX545 form | one-phase SGX535 emit | yes | 0x0d800000, b2 |
| one-phase SGX535 emit (`emit.t1 r0, #n`) | either, or the empty task | yes | **0**, b1 |
| one-phase, three emits | either, or the empty task | yes | 0x0d800000, b2 |
| one-phase, three emits; header 0x54c3, or the pointer +4 / +0x40 | | yes | 0x0d800000, b2 |
| `phas.i` + the SGX535 emit, with the triangle | one-phase | no | 0xd000, b1 |

What fits all of it **(G, the working model)**: on the SGX530 the address the MTE fetches
the state from is the **value of the final `emit.t1`'s src0**. Our ending passes `o0` there
(the header, or with `STATE_PTR` the block's address); the SGX535's ending passes `r0`,
which is 0 here. The b2 fault at the page under `PDS_EXEC_BASE` comes after a good fetch
and doesn't depend on the record's contents or a small shift of the pointer.

### DOUTU word 0 b4 is code address bit 15, not a flag (C)

`SGXGEN_DOUTU_B4` (b4 on every MTE-emitting task's DOUTU, as in the 530 vendor stream) took
the 0xd000 fault away, but only because the tasks no longer fetch their code: a USSE code
fault (requestor b2) at code base 10 + 0x8000 + the code's offset, wherever the code sits:

| code ring (`SGXGEN_CODE_RING`) | fault |
|---|---|
| 0x4000 | 0x0fc0c000 |
| 0x2000 | 0x0fc0a000 |
| 0x1000 | 0x0fc09000 |

So on the SGX530 DOUTU word 0 b4 adds 32 KiB to the code address: the vendor sets it
because its MTE-emitting code sits in the upper half of a 64 KiB region. That makes the
offset field 16 bits wide (64 KiB) with b4 its bit 15. **docs/PDS.md's "byte offset at b4,
under 32 KiB" needs this correction.** It doesn't change the 0xd000 fault.

## Where this leaves the 530 (23:40 UTC; board released for another session's slot)

1. **Fixed, needs landing:** 0xa74 needs b22-27 nonzero (0x05208200 runs) for the PDS to
   issue MTE-bound tasks. A per-core init value, in the driver's SGX530 init script.
2. **Open:** the MTE takes the state task's first output word as the address of the state
   record (C). Every emit ending tried gives the same fault, so it isn't the final emit's
   form. Emitting the record's address makes the MTE fetch it and run on into a PDS
   fetch at offset 0 (also C), which suggests this "fetch through a pointer" path is a
   different mode from the one the vendor uses, not the right one. Best next hypotheses:
   - (a) the state task's DOUTU words 1/2 (the vendor's state-emit DOUTU has b21; its w1/w2
     on the 530 are unexplored) select how the MTE treats the task's output;
   - (b) the VDM state word's info form (0x2a200 | dwords) has a field on the 530 for
     "data follows" vs "address follows"; sweep bits 8-17 (the vendor's per-program
     0x2a2 / 0x161 / 0x2c2) with 0xa74 fixed, where the earlier sweep ran without it.
3. Not causes (null with 0xa74 fixed): the SGX535's one-phase emits, primary-attribute
   DMA, BIF_3D_REQ_BASE at TA start, the clear's region-clip group.

## Second slot (23:52-00:20 UTC): hypotheses (a) and (b), both null

Clear only, 0xa74 = 0x05208200, new modules with `probe_vdm_ctl`.

- **VDM control 0x23c** = 0xa2, 0x82, 0x122, 0x180 (0x1a2 control): the same 0xd000 fault.
- **Microkernel variants** (no 0x218 b24, 0x250 = 0x88, the SGX535's TE set): the same.
- **(b) State VDM info word, bits 8-17 flipped one at a time:** b10 and b11 bring back the
  old hold at the state program; b13 clear faults at 0; every other bit is unchanged.
  The info form decides whether the update is admitted, not how the MTE reads it.
- **(a) State DOUTU words 1/2** (w2 = 1, w1 = 0x04000000, w1 = 2, w1 = 2 + w2 = 1): the same.
- **`STATE_PTR` at a buffer of one value** (0, 0x1000, 0x10000, 0x0e001000): the PDS fault at
  0x0d800000 (b2) every time, so the follow-on PDS fetch at offset 0 doesn't come from
  the fetched words.

Still open: what makes the SGX530 MTE take the state task's output as data rather than as
an address. Untested: the region-clip/pixel words in the 535's exact form (secondary
without rows, DMS 0x30000), the draw entry without b23 and its range word, and the
probe_init host values (0x804 = 0xffff, 0xa00 = 0x7c000, 0xaac/0xabc).

## Third slot (2026-11-16 01:03-01:20 UTC): the three leads left, all null

Clear only, 0xa74 = 0x05208200, modules with `probe_init`, image `sgx530_inv23`.

| variant | result |
|---|---|
| `probe_init` = the public SGX535 driver's bootstrap set (0xca0 = 0xc07c, 0x13c, 0xa7c, 0xa80, 0xa78 = 0, 0xaac = 0x44, 0xabc = 0xc, 0x804 = 0xffff, 0xa00 = 0x7c000) | timeout, no fault, the TA never kicked |
| 0x804 = 0xffff alone | the same: the microkernel consumes 1 of 3 commands (TA clock off, no TRIG_TA, 0x218 and 0x700 untouched) |
| 0xa00 = 0x7c000 alone; 0xaac/0xabc/0xa78 alone | the 0xd000 fault |
| `SGXGEN_PIX535` (secondary word without rows, DMS 0x30000) | the 0xd000 fault |
| `SGXGEN_RGN535` (region clip 0, 0) | the same |
| both | the same |
| `SGXGEN_DRAW535` (draw entry without b23 and its 0x003fffff word) | the same |
| all three | the same |

So 0x804's low bits stop the open microkernel before the TA on this core (the SGX545
value is wrong here, which is why the SGX530 init script leaves it out). None of the
SGX535's state-record, draw-entry or host-init forms changes how the SGX530's MTE reads
the state task's output.

**Where it stands.** The 530 gets as far as the MTE with 0xa74 b22-27 set. The MTE takes
the state task's first output word as the address of the state record (C), whatever the
emit encoding, VDM control, info-word form, DOUTU words, record contents or draw form.
Everything public about the SGX535 that bears on it is now matched or tried. The next
step needs new information about the SGX530's MTE input: what the vendor's state-emit task
does (its code is in the USSE heap the 2026-11-14 capture skipped), or a structured
search of the emit instruction's remaining fields with the pointer probe as the detector.
