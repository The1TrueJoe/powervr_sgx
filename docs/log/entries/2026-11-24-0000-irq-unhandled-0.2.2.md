# The 0.2.2 kernel slowdown: every interrupt returned unhandled

2026-11-23/24, a CE5300 board (SGX545 rev 1014), the 7.3.3 test kernel from CI run 44636358426
RAM-booted, and powervr_sgx loaded once per boot from one of two CI builds: 0.2.1's driver (run
43666934038) or 0.2.2's (run 44636358426). The kernels' drm_exec, drm_gpuvm and gpu-sched
modules are byte-identical, so either powervr_sgx loads on the same kernel. Issue #5: on
Cedarview the 0.2.2 module is about 5% slower in a CPU-bound OpenArena timedemo whichever
Mesa runs, and a tester's desktop lag went away with the 0.2.1 kernel.

**Bench:** `mesa/tests/sgx_submitbench -t 4`. One triangle per iteration into one of four 64x64
FBOs in turn, so each iteration is a render job of its own (with one target, the driver defers
the flush). Dev Mesa 504913f6. Boots alternated b, a, b:

| module | us a submit (wall) | us system time a submit |
|---|---|---|
| 0.2.1 | 214.7, 214.7, 221.9 | 49.7-67.1 |
| 0.2.2 | 2028-2052 (6 runs) | 151-158 |
| 0.2.2 with this fix | 209.4, 220.7, 223.3 | 63.4-70.7 |

The fixed module is CI run 45299185489's, on that run's own kernel. Its config gained CMA and
the HDMI helpers from the board tree, and its drm_exec, drm_gpuvm and gpu-sched match the
other two runs byte for byte.

**Cause:** `pvrsgx_irq()` since 806cacaa (the Clover Trail MSI) counted its events in the test
that ends the loop, `if (!sdev->vdc || ++events == 4) break;`. Without the display's latch
(CE5300, and Cedarview through gma500's callback) the count never ran, and the handler returned
`IRQ_NONE` for every interrupt it handled. Nothing woke the thread, and each finished job waited
for the poll backstop. `/proc/interrupts` showed the interrupts arriving: 10432 on line 26
after the runs. After enough of them the kernel's "nobody cared" check would turn the line off.

**Not the cause:** the debugfs render tracking (7201768f), which was the obvious hot-path
change in the diff.

A rmmod and insmod of powervr_sgx in a loop wedged the board on the first swap (2026-11-23,
power-cycled by hand). Each module was then loaded once per boot.
